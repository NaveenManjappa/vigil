# The Investigator reaches the evidence through three tools bound to the Case's Account

The Investigator is a MAF `ChatClientAgent` that is told the Alert up front and fetches everything else itself. The Enrich step gives it the Score, Risk Band and Rule Hits, each citing the Evidence Refs of the events behind it, with those events listed. It then has three tools: `GetAccountTimeline(days)`, the Account's events in the last `days` days up to its latest event (event time, capped at 90 days to bound tokens); `QueryGraphNeighbourhood()`, the Account's Neighbourhood; and `GetHolderBaseline()`, the Holder's usual countries, devices and logins per week from before the earliest event any Rule Hit cites. That is the GraphRAG of PROJECT.md: the model retrieves relational facts from the Projection and reasons over them, instead of being handed a graph dump.

The tools take no account argument. They are built per Investigation around the Case's Account and handed to the agent per run, so the model cannot ask about another Holder whatever it is told; the agent itself, with its stable Id `vigil-investigator` and name `Investigator`, is built once. Every tool result is written by `MaskedEvidence`, which registers the identifiers it is about to show, gives each new event an `E-n` ref and each graph fact a `G-n` ref, and masks the text (ADR-0008). Everything the tools read comes through `IInvestigationSource`, raw, so masking lives on the agents' side of the interface and no implementation can forget it. Beyond timeline, neighbourhood and baseline it has `GetEventsAsync(eventIds)`, because Enrich must show and register the events a Rule Hit cites, and a Graph Rule's evidence includes other Accounts' events that no timeline of this Account would return.

The Neighbourhood is one hop, like the Graph Rules (ADR-0014): each of the Account's Linking Identifiers, the other Accounts on it, and whether each is Confirmed Fraud. IP addresses and Addresses are left out, as they are from the Graph Rules, so the model is never shown an innocent household or office as a link. An identifier no one else uses is kept, because "the new bank account is unshared" is evidence too. Each identifier is one `G-n` fact standing for this Account's link event and each other Account's.

PROJECT.md listed five tools; two are dropped. `GetRuleHits` repeats what Enrich already gives, and `GetKnownFraudMatches` is the Confirmed Fraud flag on the Neighbourhood. Fewer tools mean shorter tool schemas on every round trip and fewer wrong turns for the model.

The instructions are `config/prompts/investigator.v1.md`, embedded in Vigil.Agents so the prompt in force always matches the Prompt Version `investigator.v1` recorded with it. The Fake provider plays a scripted Investigator when it sees these tools: one `QueryGraphNeighbourhood` call, then a Finding citing the brief's E-refs and the graph facts that touch Confirmed Fraud, so the free demo shows a tool call in the trace and passes validation.

## Considered Options

- **All evidence in the first prompt** (no tools): one call and simpler, but it pays for the whole timeline and graph on every Case and shows no tool calling, which the demo exists to show.
- **Tools that take an AccountId**: more flexible, but the model could be talked into querying another Holder, and binding in code is the only control that cannot be prompted away.
- **Two-hop or whole-component neighbourhood**: more context for rings, but a second hop mostly reaches innocent Accounts through a shared device (ADR-0014), and the token cost grows with the graph.
