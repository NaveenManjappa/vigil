# The Investigation is a MAF workflow that pauses at Await Approval, checkpointed in Postgres

Each Case's Investigation runs as a Microsoft Agent Framework workflow, `InvestigationWorkflow`: Enrich → Investigate → Await Approval → Act. Enrich builds the masked brief (ADR-0008). Investigate hosts the Investigate, Validate and Review loop with its one retry (ADR-0006); the loop returns an outcome on every path, LLM failures included. Await Approval is a `RequestPort` whose request is the masked outcome (Finding, flags, Pseudonym map, Evidence Refs with their EventIds, token usage, Prompt Version) and whose response is the Analyst Decision `{ outcome, action, analystId, notes }`. Act runs the `IActStep` hook, `ActStep` in the API, which records the Analyst Decision, its Intervention (BlockBankChanges until a date, `Intervention:BlockBankChangesDays`, default 7; ContactHolder; none for NoAction) and the DecisionRecorded and ActionTaken Audit Entries, closes the Case, and for a ConfirmedFraud outcome records a Confirmed Fraud with source Analyst. It enforces nothing. The runner writes the InvestigationCompleted and ReviewCompleted Audit Entries with the Case when it reaches AwaitingApproval.

The worker's `IInvestigationRunner` runs the workflow until it waits on the approval request, then stores the request with the Case and moves it to AwaitingApproval. It does this only after the stream ends, which is after the superstep holding the request has been checkpointed, so an AwaitingApproval Case always has a checkpoint to resume. `POST /cases/{id}/decision` is accepted only in AwaitingApproval (otherwise 409). It rebuilds the workflow, resumes from the Case's latest checkpoint and answers the re-emitted request, which keeps its RequestId across a restart; no model is called on resume. Act's writes are one transaction, and for a ConfirmedFraud outcome they share the Confirmed Fraud's transaction (decision first, then the record, graph projection and Neighbour re-scoring), so if Act fails the endpoint fails, nothing is kept, the Case stays AwaitingApproval, and the decision can be posted again. A decision run keeps the checkpoints it writes in memory (`DecisionCheckpointStore`), so the pause stays the Case's latest stored checkpoint: a run resumed from a checkpoint past Act would have no request to answer and would wait forever. So two decisions that both pass the AwaitingApproval check both reach Act. If the first is still in flight, `analyst_decisions`, keyed by CaseId, lets only one insert; if it has committed, Act finds it on the Case and refuses rather than replace it. Either way the loser fails before anything reaches the graph and gets 409.

Checkpoints go to the `workflow_checkpoints` table through `PostgresCheckpointStore`, one row per superstep, with the CaseId as the MAF session id. Rows are ordered by an identity column, so the last row is the latest checkpoint. The payload is `json`, not `jsonb`: jsonb reorders keys, and System.Text.Json reads a polymorphic value only when its type marker comes first.

The Enrichment holds live objects (the masker and the ref table the tools add to), which cannot be serialised. So it passes from Enrich to Investigate by reference, through an object shared by the two executors of one built workflow, and the message between them carries only the CaseId. This is safe because a workflow is only ever resumed from Await Approval. A run interrupted before then leaves the Case Investigating, and the startup re-queue (ADR-0004) starts it again from the beginning.

## Differences from PROJECT.md and the MAF docs

- **Version:** MAF 1.26.0, not 1.13.0 (ADR-0009).
- **Custom checkpoint store:** MAF ships in-memory and file stores, not a database one. `PostgresCheckpointStore` subclasses `JsonCheckpointStore` and is wired with `CheckpointManager.CreateJson(store, options)`. The store creates the checkpoint ids itself.
- **Checkpoints are bound to code identity.** A checkpoint records each executor's id and the assembly-qualified name of its type, including the assembly version. Renaming or moving an executor class, changing an executor or port id (`enrich`, `investigate`, `await-approval`, `act`), or changing the agent Ids and Names (`vigil-investigator`/`Investigator`, `vigil-reviewer`/`Reviewer`) strands every Case already waiting. They are constants for that reason.
- **`Executor<TIn,TOut>` instead of `[MessageHandler]`:** the attribute pattern that Learn shows needs the separate source-generator package and partial classes. Subclassing `Executor<TIn,TOut>` or `Executor<TIn>` needs neither. An executor that yields workflow output must say so with `[YieldsOutput]`, or the yield throws.
- **Watching a paused run:** in 1.26.0, `WatchStreamAsync(ct)` blocks while a request is pending, so the first run would never return. The first run uses `WatchStreamAsync(blockOnPendingRequest: false, ct)`, which ends once the run is waiting. The resumed run blocks, waits for the response it sends, and returns when Act yields its output.
- **Executors must not throw** on an expected failure: an exception that escapes an executor ends the run with no approval request. LLM and parse errors are therefore turned into InvestigationFailed inside the loop. Only infrastructure errors in Enrich or Act escape, and those fail the run, so that it can be retried.

## Considered Options

- **Our own state machine over Case columns, no MAF workflow:** fewer moving parts, but it would not show MAF's human-in-the-loop and checkpointing, which the build exists to demonstrate.
- **`jsonb` payload:** queryable and compact, but the key reordering breaks polymorphic deserialisation; the payload is never queried.
- **Store the Enrichment in workflow state:** this would allow resuming between Enrich and Investigate. But the masker and the ref table would need a serialisable form, for a resume point nothing needs: re-running an interrupted Investigation costs at most one Case's tokens.
- **Resume from a checkpoint id stored on the Case:** precise, but "latest for the session" is the same checkpoint while the Case waits, and it needs no extra column.
