# The graph is a disposable Projection, updated inside ingestion

Postgres is the source of truth; Neo4j holds a Projection of it. Inside the ingest request, after the batch is appended and before the Postgres commit, every event in the batch is MERGE'd into Neo4j: Holder OWNS Account, and Account linked to its Device, IpAddress, Email, Phone, BankAccount and Address. Email, Phone, BankAccount and Address come from the NewEmail, NewPhone, NewBankAccountHash and NewPostcode attributes. There are no Registration or Transaction nodes, because they link nothing.

Projecting in the request means that by the time the request returns, the graph already reflects the batch, so the graph Rules planned for Stage 2 can score in the same request. A Neo4j failure fails the request and rolls back Postgres; the client's retry is safe because ingestion is idempotent on EventId and MERGE is idempotent on node keys. The two stores are not one transaction: if Neo4j commits and the Postgres commit then fails, the graph briefly holds links for events that are not stored. We accept that, because the client retries a failed request and the graph is disposable, so a rebuild from Postgres removes anything stray. The whole batch is projected, including events already ingested, so a retry after a Postgres commit failure still reaches the graph, and so do events from before Stage 2 when they are posted again. Each batch is one Neo4j write transaction, and uniqueness constraints on every node key are created at API start so concurrent MERGEs cannot create duplicate nodes.

In a graph, one Account's event can change another Account's risk: when B adds a bank account A already pays out to, A has G1 too. So after projecting, ingestion asks the graph for the batch's neighbours, the Accounts outside the batch linked to any Linking Identifier on the batch's events, and re-checks them in the same transaction: it fetches their Graph Rule Hits and re-runs Detect with their stored Alerts, which can only append hits (ADR-0013). Without this, the first Account on a shared bank account would never get G1. Every identifier on the batch counts, not just new links, which keeps the lookup simple at the cost of re-checking a busy shared device's Accounts on each event that uses it; the Detector makes a re-check with nothing new a no-op.

Recording a Confirmed Fraud works the same way: the record goes to Postgres (keyed by AccountId, so recording twice keeps the first decision), its Case is MERGE'd into the graph, and the fraud Account's neighbours, the Accounts sharing a Linking Identifier with it, are re-checked, since each may now have G2. The Case MERGE matches a pattern, which no uniqueness constraint can protect, so the fraud Account's advisory lock serialises it. Confirmed Fraud is not an event, so a rebuild replays the `confirmed_frauds` table as well as the event store.

Each Account is scored under its advisory lock. Neighbours are only known after projection, so their locks are taken after the batch's own, each set in sorted order. Two batches that link to each other's Accounts can therefore deadlock. We accept that: Postgres detects the deadlock and aborts one transaction, Npgsql treats the error (40P01) as transient, and the execution strategy replays the whole request, which is safe because appending and projecting are idempotent.

The rebuild-graph command, the API binary run with `rebuild-graph`, restores the Projection after Neo4j data is lost or the projection model changes. It wipes Neo4j, drops every constraint so none is left for an old label, recreates the constraints, re-projects every event from Postgres, then every Confirmed Fraud. Replay order does not matter because projection is order-independent: a link keeps its earliest `firstSeen`, and on an exact tie the lower EventId, not the first to arrive, so the rebuilt graph gives every Account the same graph Rule Hits as the live one. Alerts are not re-scored, because they are append-only (ADR-0013). Rebuild with ingestion stopped: a batch scored against a half-built graph would miss hits, and those Alerts would stay low. The AppHost runs it as an explicit-start resource, like the simulator.

Relationships carry only `firstSeen`, kept as the earliest OccurredAt even when events arrive late, and `firstEventId`, the event that set it, which Graph Rules cite as evidence (ADR-0014). PROJECT.md Section 8.1 drew `from`/`to` and `lastSeen` periods; they are dropped because no Rule reads them, and an old email simply stays linked, which is what "email previously used by a fraudster" needs.

## Considered Options

- **Project after commit, or from a background worker**: ingestion stays fast and Neo4j outages don't block it, but the graph lags the event store, and an Alert returned by the request could not include graph evidence.
- **Neo4j as the store of record**: one store, but it gives up the event store's append-only, idempotent guarantees (ADR-0010), and the graph could no longer be wiped and rebuilt.
- **Lock neighbours before projecting**, so all locks are taken in one sorted pass and cannot deadlock: the neighbours would have to be found before the batch's links exist, which misses Accounts that become linked by the batch itself (the case this re-check exists for).
- **Re-check neighbours after commit, or from a background worker**: no cross-Account locks in the request, but the first Account on a shared bank account would be lifted later than the Account that linked to it, and a crash in between would lose the re-check.
- **Rebuild by re-posting events through the API**: no new command, but every batch would be re-scored, and a Confirmed Fraud would only reach the graph if it were re-posted too.
