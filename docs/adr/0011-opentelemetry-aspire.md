# OpenTelemetry with the Aspire dashboard for local observability

All services call `AddServiceDefaults()`, which wires OpenTelemetry traces, metrics and logs plus health endpoints. Locally these go to the Aspire dashboard, which needs no account and no cost. In production the same telemetry goes to Application Insights by changing the exporter, not the instrumentation.

Aspire is local orchestration only (it starts Postgres, Neo4j, the API and the simulator); it is unrelated to Microsoft Agent Framework.

## Investigation telemetry (Stage 3)

Vigil's own spans and metrics use one name, `Vigil`, for the ActivitySource and the Meter (`VigilTelemetry` in Vigil.Domain, the project every other one references). The chat client is instrumented with `UseOpenTelemetry(sourceName: "Vigil.Llm")` and each agent with `UseOpenTelemetry(sourceName: "Vigil.Agents")`; the workflow uses MAF's `WithOpenTelemetry`, whose source is `Microsoft.Agents.AI.Workflows`. ServiceDefaults registers these names explicitly rather than MAF's `Experimental.*` defaults, so a framework rename cannot silently drop agent spans. Sensitive data stays off everywhere: prompts are masked, but would bloat the trace and appear twice.

- **Spans:** `graph.project`, `graph.neighbours`, `detect` (one per scored Account) and `graph.rules` under the ingest request. `detect` is started in ingestion, not inside the Detector, which stays a pure function that evaluation calls thousands of times.
- **One trace:** the worker starts `investigate case` with the `ActivityContext` queued with the Case as its parent. Because it is current when the workflow run starts, `workflow.session`, the executors, `invoke_agent Investigator(vigil-investigator)` with its `chat` and `execute_tool` spans, and `invoke_agent Reviewer(vigil-reviewer)` all join the ingest request's trace. A Case re-queued at startup has no parent, so its Investigation is a root trace of its own.
- **Decision trace:** the Investigation span's W3C traceparent is stored on the Case (`InvestigationTrace`). `decide case` runs under the decision request's own trace with an `ActivityLink` to it, so an approval that waits for days does not stretch the Investigation trace across them.
- **Metrics:** `vigil.llm.tokens` (counter, tags `agent` and `direction`), `vigil.llm.cost` (histogram, £ per Investigation from `Llm:InputPricePer1kTokens` and `Llm:OutputPricePer1kTokens`) and `vigil.investigation.duration` (histogram, seconds to Await Approval). They are recorded once per Investigation from the usage the workflow returns, not per round trip in `TokenLoggingChatClient`: below the agents the client cannot tell which agent called it, and per-call tokens are already logged there. The meter comes from the host's `IMeterFactory`, so each test host has its own instruments.
- **Evaluation (Stage 4):** the Judge and the Scenario Generator are instrumented with the same `UseOpenTelemetry(sourceName: "Vigil.Agents")` as the Investigator and Reviewer, so if the evaluation process is pointed at an exporter its spans sit beside theirs. Their token usage is logged per call by the same `TokenLoggingChatClient`.
- **Observed in MAF 1.26.0:** with both layers instrumented, the `chat` spans appear under the `Vigil.Agents` source rather than `Vigil.Llm`; both are registered, so nothing is lost.
